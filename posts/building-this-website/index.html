Building a personal website no longer requires learning web development from scratch first. With a coding agent such as Codex or Claude Code, you can describe your requirements, create pages, adjust layouts, and set up publishing, then refine the result through previews.

Still, “build me a website” leaves many decisions to the tool. Where should articles live? Where will the site be hosted? How will you update it? Does your computer need to stay on?

This article uses the website you are reading as an example. It introduces the main components and their roles, so you can use its architecture as a reference, describe what you want, and work with a coding agent on the implementation.

The big picture: from articles to a website
#

The basic process is to turn text files and templates into pages, then let a hosting platform serve them to readers.

Articles, images, settings + Blowfish theme
                    ↓
          Hugo generates the site
                    ↓
       HTML, CSS, JavaScript, images
                    ↓
        GitHub Pages / Cloudflare
                    ↓
             Reader's browser
ComponentIts role on this site
MarkdownHolds articles and page content
HugoCombines content, settings, and templates into website files
BlowfishProvides the appearance and common reading interfaces
Git / GitHubStores source files and revision history
GitHub ActionsAutomatically builds and publishes updates
GitHub PagesHosts the primary public website
CloudflareHosts another copy as a mirror
Codex / Claude CodeHelps connect the components, adjust the design, and check results

To begin, you can use Hugo, a theme, and one hosting platform. Publishing to two platforms is a choice made for this site; you do not need both from the start.

Static websites: prepare the pages before readers arrive
#

A static website has its main page content generated before publication. When someone opens an article, the server sends existing HTML, styles, and images, which the browser displays.

Think of it as a typeset ebook: after adding or editing content, you generate an updated copy and put it online.

This works well for personal profiles, research publications, portfolios, technical notes, and blogs. Their content is usually updated by the author, so there is little need to assemble each page from a database whenever someone visits.

Maintenance is relatively simple, too. This site does not require me to manage a continuously running application and database. Once published, it remains available even when my computer is off.

“Static” does not mean the page cannot move. The galaxy, terminal, and raven interactions on this site run as JavaScript in the browser. Theme switching, expandable content, and article search using a prebuilt index can also work on a static site.

Features that need server-side processing require additional planning: signing users in, storing individual users’ data, or collecting payments, for example. If your main goal is to present your work and write articles, a static website is an approachable starting point.

Hugo: turning content into pages
#

Hugo is a static site generator. You supply articles, images, settings, and templates; it combines them into a complete website.

Articles are mainly written in Markdown, a text format with simple formatting markers. For example, ## introduces a section heading, and **text** makes text bold. The source remains readable and is easy to work on with a coding agent.

An article might look like this:

---
title: "My first article"
date: 2026-10-05
draft: true
---

This is the opening paragraph.

## Why build a website?

I want somewhere to collect my work and notes. ...

The information between the two --- lines is called front matter. It tells Hugo the title, date, and whether the article is a draft. The body follows below.

Hugo also supports multilingual websites. This site’s English and Traditional Chinese pages are written separately and linked through the language switcher. The translations still need to be prepared and checked; Hugo organizes them and generates the pages.

For everyday writing, you edit the content while templates take care of navigation, footers, and article layout. As the collection grows, this avoids repeatedly editing the same elements on individual pages.

Blowfish: start with a complete design, then make it your own
#

Hugo generates the website; the theme supplies its presentation. This site uses Blowfish, a Hugo theme with article layouts, navigation, and light and dark appearances.

A theme gives you a usable site early on. You can add a profile and a few articles, check the structure, and then adjust typography, colors, the homepage, and interactions.

The current homepage includes custom elements such as a research galaxy, a profile panel, and an ASCII raven. These build on the theme: I used Codex to modify HTML templates, CSS, and JavaScript to create the appearance and interactions I wanted.

For example, you could ask:

Use a dark background on the homepage. Show my name, research interests, and contact details first. On mobile, place those details before interactive decorations. Keep article pages quiet and easy to read.

Specific requirements make it easier to judge the preview. Once you can see the result, refine it one change at a time.

GitHub and GitHub Actions: save the content and automate updates
#

Git records file changes, and GitHub hosts Git repositories. Changes to articles and designs can have a recorded history, making it easier to compare revisions or recover an earlier version.

This site keeps source content and editing history in a private repository. The public repository contains only the generated website files. Readers can access published pages, while drafts, internal notes, and other working files do not have to be published alongside them.

GitHub Actions automates building and publishing. When I push an update to the source repository, GitHub starts a build environment, runs Hugo, and sends the generated files to the hosting platform.

An everyday update therefore becomes: edit an article, preview it locally, push the changes once satisfied, and check that publishing succeeded.

GitHub Pages: giving the website a public address
#

After generating the files, you need somewhere readers can access them. GitHub Pages is GitHub’s static website hosting service.

Its role differs from the repository: the repository stores files and revisions, while Pages serves website content through a URL. This site’s primary address is https://yenjia.github.io/.

You can start with the address provided by the platform. If you later want your own domain, you can add the domain and DNS configuration. The domain is the address readers enter; the hosting platform supplies the website files.

The initial setup connects Pages with the publishing workflow. A coding agent can help with those settings, but you should still open the production URL after publishing and check the homepage, articles, images, and links.

Cloudflare: hosting the same content on another platform
#

Cloudflare provides several website and networking services. For static sites, you may encounter Cloudflare Pages or Workers Static Assets. Both can host website files, but their setup and deployment methods differ.

This site’s Cloudflare mirror uses Workers Static Assets. The deployment tool Wrangler uploads the files generated by Hugo. This configuration serves static content without an additional backend program for application logic.

Cloudflare Pages also allows you to upload a prebuilt website. When setting up hosting, identify which service you are using and ask the agent to follow the corresponding documentation.

On this site, GitHub Pages and Cloudflare are independent entry points built and deployed from the same source content. Cloudflare acts as a mirror. It does not sit in front of GitHub Pages, and automatic failover is not configured.

After setup, how do you write the next article?
#

Once the website is ready, most of your time can go into content. Here, articles live in content/posts/. Add a Markdown file with a title, date, and body, and you have the source for another article.

While writing, keep draft: true so ordinary production builds skip it. Locally, preview with drafts included:

hugo server --buildDrafts

This command starts a local preview and prints its URL in the terminal. If a coding agent handles the operation, you do not need to memorize the command. It does not publish the article online. Once the content is ready, change the draft flag to false and use the existing publishing workflow.

For English and Chinese versions, you can follow this site’s naming convention: my-first-post.md and my-first-post.zh-tw.md. Place images in the project’s image directories and reference them from the article. An agent can follow the existing project structure rather than inventing a new arrangement each time.

The initial setup connects the components; later articles reuse that workflow. You can focus on writing and ask the agent for changes when you need a new layout or feature.

How to describe the project to Codex or Claude Code
#

Once you understand the components, you can give the agent an architecture, content requirements, and completion criteria together. Here is a starting prompt:

Build a personal website with Hugo and Blowfish, including a homepage, an About page, an article list, and research publications. Manage content in Markdown, support English and Traditional Chinese, use a dark appearance, and make it comfortable to read on mobile. Set up GitHub Actions to publish automatically to GitHub Pages. Complete local previews and build checks first, summarize the changes, and wait for my confirmation before publishing. Keep source files in a private repository and publish only generated website files. Store credentials in the platform’s secrets settings.

After the first version, assign another focused task, such as: “Display homepage publications as three cards, stacked in a single column on mobile.” Once the content and appearance are stable, add Cloudflare deployment or more elaborate interactions.

Look at the result after each round: is the text readable, does the mobile page scroll sideways, does language switching work, and are images and links intact? Ask the agent to check keyboard operation for interactive elements and ensure content remains accessible when users request reduced motion.

You do not have to memorize every command, but it helps to know which layer you are changing: content, appearance, or publishing. That makes problems easier to describe and proposed changes easier to understand.

These roles connect to make this website: Markdown holds content, Hugo and the theme generate pages, GitHub records changes, Actions automates builds, and hosting platforms provide public access. Prepare the content you want people to see, choose a simple publishing route, and work with a coding agent on the first version. You can develop it into your own website over time.
