>_ Before reading

What does this post answer?

  • It is written for people who want to start using AI tools (mainly Claude Code here), with a background close to lab research.
  • It does not teach installation or commands; it sets out when I find these tools useful, why, and what to watch for.
  • Research content is kept abstract; the experiment loop is detailed in the earlier workflow log.

Where I have used Claude
#

I mainly use two of them: Claude (web/app) for everyday questions, and Claude Code (terminal) for research work and anything else that can be done on a computer. None of this is specific to Claude, though; most AI agents from other companies can now do these tasks too.

So far, the scenarios I have tried fall roughly into these groups:

  • Generating ideas: brainstorming topics and listing possible directions.
  • Research: reading and organizing existing projects and literature, and picking up work from existing documents and scripts.
  • Slides and documents: connecting Claude to Google Drive to edit Google Docs and Slides directly.
  • Linux: installing packages, adjusting configuration, tuning laptop performance, fixing bugs. I think Linux suits this kind of AI agent especially well: whatever the terminal can do, Claude can mostly do for you.
  • This personal website: the one you are reading.
  • Improving my own workflow: for example, having Claude read back through its own session history to find habits worth changing.

How well these went varied a lot. Looking back, two things mostly decided it: whether the result can be verified, and how much human judgment it needs.

Understand the environment Claude Code works in
#

A few concepts first; the methods later follow from them.

A folder is a workspace
#

Claude Code treats the folder it starts in as the project. It can read the files there and looks there for instruction files such as CLAUDE.md. So “one project, one folder” is already a way of organizing work. By default it rarely wanders outside this workspace on its own; if you need stricter isolation, Codex, for example, offers a stricter sandbox.

The harness decides what it can do
#

The same model behaves very differently inside different harnesses: Claude on the web, Claude Code, and other vendors’ coding agents each provide different tools, permissions and memory, with their own strengths and weaknesses. Most of their abilities are similar; compared with Codex, I prefer how Claude Code handles long tasks.

A harness is roughly made of these parts:

  • The model: thinks and decides the next step, for example Opus or Sonnet.
  • System prompt: tells the model its role, how to work, and the rules.
  • Tools: reading and writing files, running commands, searching the web, or connecting to outside services such as Google Drive through MCP.
  • Permissions and sandbox: which actions need your approval first, and what it is allowed to touch.
  • Context management: which instruction files are loaded at the start, and when to compress a conversation that has grown too long.
  • Instruction files and memory: CLAUDE.md, automatic memory and other information kept across sessions.

Inside this shell the model repeats “call a tool → look at the result → decide the next step” until the task is done. So the same model in a different harness is like the same person moving to a lab with different equipment.

Context is a limited resource
#

What Claude can see in one session (its context) has a limit. The longer a conversation runs:

  • The more it costs: every turn reprocesses everything before it, so quota drains faster.
  • The more it forgets: near the limit, older content is compressed into a summary and details are lost; rules given earlier may also be ignored.

Caching: why long conversations stay expensive even with cache hits
#

I said above that every turn reprocesses everything before it. In practice Claude uses prompt caching: recently processed content is kept for a while, and if the next turn starts with the same content, that part is read from the cache at a much lower price. A few related ideas:

  • Cache hit: the start of what you send matches what is in the cache exactly, so that part is read from the cache. Matching runs from the beginning (prefix match): change anything in the middle and everything after that point has to be processed again.
  • Write and read prices: writing to the cache costs a bit more than normal input (1.25× with a 5-minute TTL, 2× with a 1-hour TTL), while reading is much cheaper (0.1× on most models, 0.05× on Opus 5.5) (Anthropic docs).
  • TTL (Time To Live): how long a cache entry lasts. The default is 5 minutes, and every hit resets the timer, so the cache never expires while you keep working. Step away longer than the TTL and the next turn has to write the whole context again, which costs more the longer the context is.
  • What breaks the cache: after a compaction, the earlier conversation is replaced by a summary, so the start has changed and the next turn is a fresh write. Switching models mid-session (say, Opus to Sonnet) also cannot reuse the existing cache.

So why not always use the 1-hour TTL? Because 1-hour writes cost 2× while 5-minute writes cost 1.25×. During continuous work, 5 minutes is enough and the extra write cost is wasted; the 1-hour TTL only pays off if you often pause for 5 to 60 minutes and come back. More importantly, the TTL only decides whether the cache expires; it does nothing about the cost of re-reading the context on every turn. The session in the example in the costs section already used the 1-hour TTL with a hit rate near 100%, and it was still expensive.

The key point: a hit is a discount, not free. Every turn reads the whole context, so a 300k-token turn costs three times as much to read as a 100k-token turn, even when everything hits.

What Claude sees at the start of each session
#

Claude itself does not remember the previous conversation. Each time a new session starts, Claude Code first puts a batch of content into the context; before you type anything, it has already “read” these. According to the official documentation, this roughly includes:

ContentWhere it livesWhen it is loaded
System prompt, tool descriptions, environment infoProvided by the harnessAt the start
Skill descriptions, MCP tool namesInstalled skills and MCP serversShort descriptions at the start; full content only when used
Global instructions~/.claude/CLAUDE.mdAt the start, shared by all projects
Project instructionsThe project’s CLAUDE.md or .claude/CLAUDE.md (including those in parent folders)At the start
Subfolder instructionsCLAUDE.md inside a subfolderWhen files in that folder are read or written
Automatic memory~/.claude/projects/<project>/memory/MEMORY.mdAt the start, first 200 lines or 25 KB only

There are three kinds of “memory” here, differing in scope and in who writes them:

  • Global instructions: written by you, apply to every project, for example “answer in Traditional Chinese” or “run the tests before committing”.
  • Project instructions: written by you (or by Claude at your request), apply only to this project. They live in the folder, so they can be synced to other machines with git and shared with collaborators.
  • Automatic memory: things Claude notes down itself while working, such as your preferences and mistakes it has run into. The official documentation says plainly that it is machine-local and does not sync across machines.

One more point: after a conversation is compressed, the CLAUDE.md at the project root, the automatic memory and the system prompt are loaded again. In other words, rules written into instruction files survive compaction; rules given only in the conversation may not. To see what is currently taking up the context, type /context in Claude Code.

Claude is good at continuing and critiquing, not at choosing a direction from nothing
#

Good at
#

  • Finding flaws: reviewing code, documents and experiment designs like a reviewer and finding the holes.
  • Specific instructions: the more detail you give, the more accurate the result.
  • Tasks that split into verifiable parts: it works best when a large task breaks into small ones whose results can each be checked.
  • Continuing something already started: given a draft or existing files, it follows the thread well; starting from a blank page is harder.

Not good at
#

  • Choosing a direction: AI produces many ideas, but human ideas are often more accurate and more valuable, and AI’s ideas often turn out to exist already. A better split is that people choose the direction and AI expands and critiques it.
  • Guaranteeing there are no bugs: the flip side of being good at finding flaws. A fresh agent almost always finds new problems, so “everything is correct” takes many iterations, not one pass.

Working methods that help
#

Managing context
#

  • One task per session: avoids the cost and forgetting of long context. Start a new session for a new topic.
  • Keep what matters in files: CLAUDE.md (project rules), PLAN.md (plan), EXPERIMENTS.md (experiment log) and so on. Conversations get compressed and sessions end, but files remain, and the next session picks up from them. Of these, CLAUDE.md is loaded automatically at every start and after compaction (see the table above); PLAN.md and EXPERIMENTS.md are not, so you can add a line to CLAUDE.md such as “read PLAN.md before starting”, or pull it in directly with @PLAN.md.

Beyond that, an experiment log tends to grow longer and longer. The best approach is to summarize EXPERIMENTS.md, for example into EXPERIMENTS_digest.md, so that a new session can read only the summary and look things up when needed.

Below is an excerpt from the CLAUDE.md of one of my prostate CT classification projects (translated from Chinese; paths, machines and result numbers abstracted):

# Prostate CT cancer classification (radiomics → DL)

> The radiomics stage is finished and frozen (`SUMMARY.md`, `EXPERIMENTS.md`,
> `outputs/`: **read-only, never overwrite**). Current work is the DL stage.

...

## Data rules
...
- Other files in the parent folder are **not read or referenced**,
  including their conclusions, code and methods.

## Split rules
- `data/split.csv` is the locked train / val / test split. **Never re-split.**
- Model selection and tuning use 5-fold CV inside train only.
- **val only evaluates a configuration already chosen by CV.**
- **test is sealed**: run it once, after the final model is frozen.

...

## Subagent rules
...
- Every subagent prompt carries the full rules: data limits, the locked split,
  test is off-limits, output paths and formats.
- Do not take subagent results on trust: the main agent recomputes key numbers
  before writing them to `EXPERIMENTS.md`.

...

The file is less about how to run things than about what must not be done:

  • Fix the evaluation rules in writing: the split is locked, model selection uses CV only, val only evaluates chosen configurations, and test is sealed and run once. When it runs the loop on its own, the easiest way to go wrong is to overfit val without noticing, or to peek at test.
  • Limit the sources of information: the parent folder holds an earlier project, and the file says plainly not to read or reference it, so old conclusions are not carried over.
  • Subagents follow the rules too: every subagent prompt carries the full rules, and the main agent recomputes reported numbers before they go into the log.
  • Freeze a stage when it is done: once radiomics was finished it became read-only, and the DL stage got its own files and folders.

The matching EXPERIMENTS_DL.md always has four parts: current status, a progress checklist, a results table, and a dated log. A new session reads the first three to know where things stand and looks further down only for details:

# DL experiment log

Pass mark: validation AUC > 0.85. Model selection uses train 5-fold CV only;
val only evaluates chosen configurations; test is sealed. Plan: `PLAN_DL.md`.

## Current status (YYYY-MM-DD)
- Best pure DL: <run>, CV <x> / val <y> (95% CI), below the pass mark.
- Bottlenecks: <subgroup A>, <confounder B>.

## Progress
- [x] datalist
- [x] reference architecture, fixed
- [x] <direction 1>, <direction 2>, …
- [ ] final test (once)

## Results table
| run_id | date | input | model | train-CV AUC | val AUC (95% CI) | notes |
|---|---|---|---|---:|---:|---|

## Log
### YYYY-MM-DD Environment and data
- **Incident**: `uv sync` removed packages outside the lock file, including
  the cuDNN library torch needs. Fixed by reinstalling; from now on always
  `uv run --no-sync`.

Some rules grew out of the log. After a uv sync once deleted the cuDNN library torch needs, CLAUDE.md gained the line “always uv run --no-sync”.

Managing direction
#

  • Plan mode and auto mode: in plan mode Claude first proposes a plan and acts only after you approve it; in auto mode it acts directly, with a model classifier approving each action in your place. Use plan mode when the direction is unclear and auto mode when the task is well defined. The difference is when the person steps in: before the work in plan mode, after it in auto mode. I find the two about equally effective. In my own work I often have extra thoughts or corrections along the way (for example, as above, fixing something that broke mid-task), which fits the auto mode habit better.

Boris Cherny, who leads Claude Code, has said that he and his team have used only auto mode for months and “can’t imagine going back” to approving permissions one by one (X post). He even calls auto mode his most important tip: because you are not constantly stopping to click approve, you can run several sessions in parallel (X post). According to the official write-up, auto mode hands approval to a model classifier, a middle ground between “a person reviews every action” and “no safeguards at all”; Boris also cautions that it is not perfectly safe, and whether to use it depends on how much risk you can accept (Threads).

  • /advisor: a Claude Code feature that lets another, usually stronger, model review the current approach at key moments, like having a consultant. Some people also think it saves quota (use a weaker model such as Sonnet by default, and set Opus as the advisor).
  • Human ideas first: think of the direction yourself, then ask Claude to extend and critique it. That works better than asking it for ideas directly.

Extending what it can do
#

  • Subagents: hand parallel work to several sub-agents to finish faster; they are also good for an independent second opinion. Each subagent has its own context and returns only its conclusion to the main session, so heavy reading and searching do not fill up the main session’s context. That is how I split the work in using several agents to brainstorm research topics: the main session only discusses with me and coordinates, while proposing ideas, challenging them and looking things up are each done by a different agent.

More subagents are not always better, though. Describing its own multi-agent research system, Anthropic notes that a single agent uses about 4 times the tokens of a chat, and a multi-agent system about 15 times, so it only pays off when the task is valuable enough. They also point out that most coding tasks have less truly parallel work than research, and that tasks which need a shared context or have many interdependencies are not yet a good fit for multiple agents (Anthropic Engineering, 2025). What suits subagents best is heavy reading, searching, or work that needs an independent opinion.

  • Skills / plugins: package a repeated workflow so it can be called directly next time. For example, I turned “update the progress-report slides from the project results” into a skill: it reads the experiment results, turns them into result pages and figures, and writes them into a fixed Google Slides format. Now I only say “update this week’s slides”, and it follows the same process without my explaining the format each time. Claude also offers many useful plugins and connectors to install. The difference is roughly:
    • Connector: lets Claude reach an outside service and read or write your data, for example Google Drive / Docs / Slides (editing documents and slides directly), Gmail, Google Calendar, or GitHub.
    • Plugin / skill: packages a way of working or a tool, for example a code review of the current changes, skills for handling PDF, Word, PowerPoint and Excel files, or front-end design guidance.
  • Remote machines: once your ssh config is set up, Claude can look for idle compute on different remote machines and run experiments there.
  • Tmux: letting Claude operate a tmux pane helps manage long-running programs and watch their output. Where something has to be typed by hand (a password, for example), this is very useful.

This loop works very well on projects with a clear, verifiable goal; details are in the earlier post.

The open question is budget and stopping: how much quota should it get, and how does it know when to stop? For now I write the stop condition into CLAUDE.md, but that requires knowing in advance where the target is.

I do not have a perfect answer for setting the budget yet. For now, a reasonable approach is to cap the number of experiments (for example, at most 10), but there is a good chance it will not reach the performance you want. So it is best to judge this for your own task.

Costs and limits
#

  • Errors and hallucinations: today’s models are much stronger than before, but they can still hallucinate or give wrong information.
  • Safeguards are sometimes too strict: some reasonable actions are blocked and need extra confirmation or a different route. Security questions, for example, may be refused (even when testing only in your own environment), and in more serious cases the account may be banned.
  • Output is not always easy to read: Claude tends toward a defensive style, with cautious sentences and many qualifiers. This is especially poor for paper writing and needs rewriting.
  • It can ignore rules you wrote down: even rules in CLAUDE.md are sometimes ignored. Keeping instruction files short and putting the most important rules first helps.
  • It is expensive: the 5-hour and weekly quotas need careful management. I give clear-cut tasks to Sonnet and tasks that need judgment or advice to Opus. Avoid long back-and-forth when much of the context is already used; compact or start a new session when appropriate (see caching above for why, and the example below for real numbers). Switch models when starting a new session, too, since switching mid-session cannot reuse the existing cache. A bigger context is not always better either. Thariq from the Claude Code team notes that on a 1M-context model, context rot (the model losing its grip on earlier details) starts around 300–400k tokens, though the threshold depends on the task; he also suggests running /compact yourself with a hint rather than waiting for automatic compaction (X article). So when you get near that range, it is time to compact or start a new session.
  • Memory does not follow you across machines or apps: when you use Claude in different places, memory does not sync on its own. A shared “second brain” that Claude manages would be useful.

A real example: what long context costs
#

Once I noticed my quota draining unusually fast over two hours, so I asked Claude to analyze the session logs. Almost all of it came from a single session spent revising a paper:

ItemValue
Model calls308 (Opus 5.5)
Average context per callabout 265k tokens (peak about 366k)
Cache reads80.9M tokens
Cache writes (1-hour TTL)0.81M tokens
Output0.31M tokens
Hit rateabout 99%

The hit rate was nearly perfect, so caching was not the problem. At API prices those two hours came to about US$29: re-reading context was 56%, cache writes 22%, and what Claude actually wrote only 22%. Re-reading the context on every turn cost about 2.6 times the output itself, and many of those calls produced nothing more than a one-line grep command.

Why was the context so large? Automatic compaction only triggered at about 370k tokens; afterwards 110–170k still remained, and it soon grew back past 300k. That cycle repeated three times in two hours, so most calls ran with 200–370k tokens of context. The growth came mainly from reading high-resolution images repeatedly, re-reading an entire online document after every small edit, and many small, fragmented commands.

The alternative: when context reaches about 150k, or a piece of work ends, write progress to a notes file and start a clean session that picks up from the notes and whatever documents it needs. I estimated this by replaying each step of the same work (figure below): average context falls from 265k to about 86k, and re-reading drops from about US$16 to about US$5. New sessions have to write their context again, so cache writes rise a little, but the total still falls by about a third. Running /compact by hand also helps, but in this log 110–170k remained after each compaction, a far higher starting point than a clean session. What matters is doing it early and keeping each piece of work’s starting point small.

These are API prices. I cannot confirm that subscription quotas count cache reads in exactly this proportion, but the direction is the same: the bigger the context and the more calls, the faster the quota drains.

Closing: people judge, AI expands
#

So far, most of the work is still human–AI collaboration, and many points need a person’s judgment. The parts that can be split into smaller tasks and verified automatically are where AI is strong, and that is also how it speeds up your own workflow. At the current pace, though, perhaps before long none of this will need to be so elaborate.
