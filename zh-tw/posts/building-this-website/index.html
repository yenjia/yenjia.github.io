想架一個自己的網站，現在已經不需要先把網頁開發從頭學一遍。搭配 Codex 或 Claude Code 這類 coding agent，可以透過描述需求，快速建立頁面、修改版型與設定發布流程，再逐步預覽與調整。

不過，如果只說「幫我做一個網站」，仍然有很多選擇留給工具決定：文章存在哪裡？網站放在哪裡？以後怎麼更新？需要一直開著自己的電腦嗎？

這篇文章就以你正在看的網站為例，介紹我主要使用的元件與它們的分工。目標是讓你看完後，能夠參考這個網站的架構，清楚描述自己要什麼，再把實作交給 coding agent。

先看全貌：文章如何變成網站？
#

這個網站的核心，是把文字檔與版型轉成可以直接瀏覽的網頁，再交給託管平台提供給讀者。

文章、圖片、網站設定 ＋ Blowfish 主題
                  ↓
             Hugo 產生網頁
                  ↓
       HTML、CSS、JavaScript、圖片
                  ↓
       GitHub Pages ／ Cloudflare
                  ↓
             讀者的瀏覽器

各個元件可以用這張表理解：

元件在這個網站裡負責什麼？
Markdown撰寫文章與頁面內容
Hugo把內容、設定與版型組合成網站檔案
Blowfish提供外觀與常用的閱讀介面
Git／GitHub保存原始檔案與修改紀錄
GitHub Actions在更新後自動建置與發布
GitHub Pages託管主要網站，提供公開網址
Cloudflare託管另一份網站，作為鏡像
Codex／Claude Code協助串接元件、修改設計與檢查結果

剛開始建站時，可以先用 Hugo、一個主題與一個託管平台。雙平台發布是這個網站的安排，起步時不必一次做齊。

靜態網站：先把網頁做好，再提供給讀者
#

「靜態網站」的意思是，網頁的主要內容在發布前就已經產生好了。讀者打開文章時，伺服器直接傳送現成的 HTML、樣式與圖片，瀏覽器再把它們顯示出來。

可以把它想成一本排版完成的電子書：新增文章或修改內容後，重新產生一份，再放到網路上。

這種方式很適合個人介紹、研究成果、作品集、技術筆記與部落格。這些內容通常由作者更新，沒有必要在每次有人開啟頁面時，重新從資料庫組裝一次。

它也讓維護比較單純：這個網站不需要自己管理一套持續運作的應用程式與資料庫。發布完成後，即使我的電腦關機，讀者仍然可以正常瀏覽。

但「靜態」不代表畫面不能動。這個網站的星系、終端機與烏鴉互動，都是瀏覽器執行 JavaScript 的結果。切換主題、展開內容，甚至用事先產生的索引搜尋文章，也都可以在靜態網站上完成。

真正要另外考慮的是需要伺服器處理的功能，例如會員登入、保存每位使用者的資料，或收取付款。若你的目標主要是展示內容與寫文章，靜態網站通常是容易開始的一種架構。

Hugo：把內容變成網頁的工具
#

Hugo 是靜態網站產生器。你提供文章、圖片、設定與版型，它就把這些材料組合成完整的網站。

寫文章時，我們主要編輯 Markdown。它是帶有簡單格式標記的文字檔，例如用 ## 表示段落標題，用 **文字** 表示粗體。內容仍然很好閱讀，也適合讓 coding agent 協助整理。

一篇文章的原始檔大概長這樣：

---
title: "我的第一篇文章"
date: 2026-10-05
draft: true
---

這裡是文章開頭。

## 為什麼想架網站？

我想有一個整理作品與筆記的地方。...

上方兩條 --- 之間是文章資訊，稱為 front matter。它告訴 Hugo 標題、日期，以及文章是否仍是草稿；下面才是正文。

Hugo 也支援多語言網站。本站的英文與繁體中文內容，可以各自撰寫，再透過語言切換連到對應頁面。翻譯內容仍然需要準備與確認，Hugo 負責的是組織和產生頁面。

平常寫作只要改內容檔案，版型就會處理導覽列、頁尾與文章排版。當文章愈來愈多時，這種分工可以省去重複修改每個網頁的工作。

Blowfish：先有完整的外觀，再慢慢改成自己的樣子
#

Hugo 負責產生網站，而主題決定它呈現的樣子。這裡使用的是 Blowfish，一個提供文章版面、導覽、深淺色介面等功能的 Hugo 主題。

選主題的好處，是一開始就有可以使用的網站。你可以先放入個人介紹與幾篇文章，確認內容與結構，再調整字體、配色、首頁布局和互動。

本站現在的首頁有不少客製設計，例如研究主題星系、個人資訊面板與 ASCII 烏鴉。這些是在主題的基礎上，利用 Codex 修改 HTML 版型、CSS 與 JavaScript，做出自己想要的外觀與互動。

例如，我們可以這樣說：

首頁採深色背景，先呈現姓名、研究方向與聯絡方式。手機版要讓這些資訊出現在互動裝飾之前，文章頁則保持安靜、容易閱讀。

需求越具體，預覽後也越容易判斷是否符合期待。看到實際畫面後，再逐項調整。

GitHub 與 GitHub Actions：保存內容，也讓更新自動完成
#

Git 是記錄檔案變更的工具，GitHub 則提供存放 Git 儲存庫的服務。每次修改文章或設計，都可以留下紀錄；改壞時，也比較容易比較差異或找回先前版本。

這個網站把原始內容與編輯紀錄放在私人儲存庫，公開儲存庫只放產生好的網站檔案。讀者會看到發布的文章與網頁，但原始專案中的草稿、內部筆記和其他工作檔案，不需要一起公開。

接著，GitHub Actions 把建置和發布變成自動流程。當我把更新推送到來源儲存庫，GitHub 就會啟動一個工作環境，執行 Hugo，並把產生的檔案送到託管平台。

日常更新因此可以變成：修改文章、在本機預覽、確認後推送，接著查看發布是否成功。

GitHub Pages：讓網頁有一個公開網址
#

產生網頁檔案之後，還需要一個地方讓讀者存取。GitHub Pages 就是 GitHub 提供的靜態網站託管服務。

它與 GitHub 儲存庫的角色不同：儲存庫保存檔案和版本，Pages 把網站內容透過網址提供給瀏覽器。本站的主要網址是 https://yenjia.github.io/。

如果只想先完成一個個人網站，使用平台提供的網址就可以開始。之後想換成自己的網域，再加入網域與 DNS 設定即可。網域是讀者輸入的地址，託管平台則負責提供網站檔案。

第一次設定時，需要把 Pages 與發布流程接好。這些設定可以交給 coding agent 協助，但發布後仍然要打開正式網址，確認首頁、文章、圖片與連結都正常。

Cloudflare：同一份內容，也可以放到另一個平台
#

Cloudflare 提供多種網站與網路服務。以靜態網站來說，你可能會看到 Cloudflare Pages，也可能看到 Workers Static Assets；兩者都能託管網站檔案，但設定與部署方式不同。

本站的 Cloudflare 鏡像使用的是 Workers Static Assets，由部署工具 Wrangler 上傳 Hugo 產生的檔案。這份設定只提供靜態內容，沒有另外加入處理業務邏輯的後端程式。

如果採用 Cloudflare Pages，也可以把已經產生好的網站上傳到平台。建站時只要確認自己使用哪一種服務，再讓 agent 依照對應文件設定即可。

本站的 GitHub Pages 與 Cloudflare 是兩個獨立的網站入口，從同一份來源內容各自建置與發布。Cloudflare 在這裡是鏡像站；它沒有放在 GitHub Pages 前面，也沒有設定成主站故障時自動切換。

架好之後，寫下一篇文章需要做什麼？
#

網站架好之後，大部分時間其實都會花在內容上。以本站為例，文章放在 content/posts/，新增一個 Markdown 檔案，填入標題、日期和正文，就有了下一篇文章的來源。

撰寫期間可以保留 draft: true，讓一般正式建置略過這篇文章。本機則使用包含草稿的預覽模式，一邊修改，一邊確認排版：

hugo server --buildDrafts

這條指令會啟動本機預覽，網址會顯示在終端機裡。如果交給 coding agent 操作，也不需要特別記住這條指令。它不會把文章發布到網路上。等內容確認完成，再把草稿狀態改為 false，交由既有發布流程處理。

如果文章有中英文版本，可以沿用本站的檔名方式，例如 my-first-post.md 與 my-first-post.zh-tw.md。圖片則放到專案管理的圖片位置，讓文章引用它們。這些路徑可以請 agent 依照現有專案安排，不需要每次重新設計。

也就是說，第一次建站需要把各個元件接起來，之後寫文章可以沿用整套流程。你可以把精力留給內容，遇到新的排版或功能需求時，再請 agent 調整網站。

怎麼把需求交給 Codex 或 Claude Code？
#

了解元件之後，就可以把架構、內容與完成條件一起交給 agent。以下是一段適合當起點的需求：

請用 Hugo 與 Blowfish 建立個人網站，包含首頁、關於我、文章列表與研究成果。內容以 Markdown 管理，支援英文與繁體中文，採深色外觀並適合手機閱讀。用 GitHub Actions 自動發布到 GitHub Pages。請先完成本機預覽與建置檢查，整理修改結果，等我確認後再發布。原始檔案放私人儲存庫，公開端只放產生好的網站；憑證使用平台的 secrets 設定。

做出第一版之後，再給它下一個範圍清楚的任務，例如：「把首頁研究成果改成三張卡片，手機版排列成單欄。」等內容與外觀穩定後，才加入 Cloudflare 部署或較複雜的互動。

每輪修改都值得實際看一次結果：文字是否容易讀、手機是否出現橫向捲動、語言切換是否正確，以及圖片與連結有沒有失效。互動元件也可以請 agent 檢查鍵盤操作，並讓減少動畫的使用者仍然能取得內容。

你不必先背熟所有指令，但最好知道每次修改的是哪一層：文章內容、網站外觀，還是發布流程。當結果不如預期時，這會幫助你描述問題，也更容易理解 agent 提出的修改。

這個網站就是由這些分工串起來的：Markdown 保存內容，Hugo 與主題產生網頁，GitHub 記錄修改，Actions 自動建置，託管平台提供公開入口。先準備好想讓別人看到的內容，選定一條簡單的發布路徑，就可以和 coding agent 一起做出第一版，再慢慢長成自己的網站。
