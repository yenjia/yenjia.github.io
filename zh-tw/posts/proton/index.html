在 Linux 上打開 Steam，挑一款只有 Windows 版的遊戲，按下 Play。幾秒鐘後，標題畫面跳出來，手把也能用。好像什麼事都沒發生。

你有沒有想過這件事情非常不可思議：遊戲沒有為 Linux 重新編譯，電腦也沒有偷偷開進 Windows，它到底是怎麼跑起來的？

Linux 上的解決方法藏在幾個總是一起出現的名字裡：Wine、Vulkan、DXVK，還有 Proton。我們現在跟著遊戲走一趟，從啟動一路走到第一幀畫面，看看每個名字在哪裡登場。

>_ 閱讀路線

從一個 .exe 走到螢幕上的畫面

本文只談 CPU 指令集相同 的情況，例如 x86-64 的遊戲跑在 x86-64 的電腦上。指令集不同時（例如 ARM 電腦），還要再多一層指令轉譯，那是另一個故事了。

先看程式為什麼離不開作業系統，再看 Wine 怎麼補上 Windows 的環境，接著拆開圖形與 shader，最後回到 Proton 與 Steam Deck。下面這張圖是全文的地圖，迷路時可以回來看看。

CPU 看得懂，為什麼系統不能執行？
#

如果把 Windows 遊戲的 game.exe 直接複製到 Linux，兩台都是 x86-64 電腦，CPU 看得懂裡面的機器指令。加法還是加法，跳躍還是跳躍，會不會因為換了作業系統就變成另一個意思？

不會。但遊戲還是不能直接執行，因為它不只是一堆計算。它要先被載入記憶體、找到依賴的函式庫，接著開檔案、開視窗、讀手把，還要把繪圖工作送到 GPU。這些事靠的都是程式和執行環境之間的約定，而 game.exe 從頭到尾只跟 Windows 簽過約。

第一個約定：怎麼把檔案變成執行中的程式
#

Windows 的 .exe 與 .dll 使用 PE（Portable Executable） 格式。檔案開頭是一段標頭，寫著入口點在哪、有哪些區段、要從哪些 DLL 匯入哪些函式；.text 區段放機器碼，.data 放已初始化的資料。想看每個欄位的細節，可以翻 Microsoft 的 PE 規格。

Linux 原生程式用的則是 ELF。在終端機直接執行 ./game.exe，Linux 核心看不懂這個格式，通常只會冷冷回你一句 Exec format error（除非系統已經設定好用 Wine 開啟 .exe）。改副檔名也沒用，檔案內容本身就是另一種結構。

第二個約定：向誰要求系統服務
#

假設今天有一個情境：遊戲要讀存檔時，不會自己去碰硬碟，而是呼叫 kernel32.dll 裡的 CreateFileW；要開視窗，就呼叫 user32.dll 的 CreateWindowExW。這些 Windows API 把規矩講得很細：參數怎麼排、字串用什麼編碼、成功回傳什麼、失敗時設定哪個錯誤碼。

PE 檔的匯入表等於寫著：「我需要 KERNEL32.dll 的 CreateFileW。」問題是 Linux 原生環境不會提供 Windows 的 kernel32.dll。就算有，Linux 開檔的方式（open、檔案描述符、errno）和 Windows 的（磁碟機代號、HANDLE、GetLastError）也完全是兩個世界。

這裡順便分清 API 呼叫 與 系統呼叫（system call）。這裡的 Windows API 是 DLL 提供的函式；系統呼叫才是進入作業系統核心的那一步。在 Windows 上，CreateFileW 會經過 ntdll.dll 再進入 NT 核心；很多 API（例如字串處理）則根本不需要核心。多數一般遊戲透過這些 DLL 要求服務，因此 Wine 主要提供相容介面與必要的核心服務行為，不需要啟動一整套 Windows 核心。

結論是：CPU 能執行指令只是起點。真正要補的，是遊戲以為一定存在的那一整套 DLL，以及它們的一舉一動。

Wine：讓程式找到熟悉的介面
#

Wine 始於 1993 年，名字展開是 Wine Is Not an Emulator，「Wine 不是模擬器」。注意到了嗎？展開後的第一個字又是 Wine，再展開一次還是同一句話，可以無限套娃下去。這種把自己放進全名的命名方式叫 recursive acronym（遞迴縮寫），是開源圈的老梗，GNU 就是 GNU’s Not Unix。

不過這個名字不只是玩笑，它說明了 Wine 的做法。如果兩邊 CPU 指令集不同，就需要額外的指令模擬或轉譯；模擬器也可能透過動態編譯加速，不一定逐條解讀。在本文的同指令集情境，Wine 通常不需要轉譯一般 CPU 指令，遊戲的機器碼可以直接在 CPU 上跑。Wine 做的是另一件事：自己重寫一套 Windows 的 DLL。它有自己的 kernel32.dll、user32.dll、ntdll.dll、gdi32.dll……名字和介面跟 Windows 一模一樣，裡面則改用 Linux 的方式把事情辦好。

一個看似簡單的 CreateFileW，Wine 就得處理磁碟機代號、大小寫、HANDLE 與檔案描述符的對應，還有錯誤碼的翻譯。像 HANDLE 所指向的檔案物件、共用模式等需要協調的狀態，會由 wineserver 協助管理，它扮演了 Windows 核心裡一部分物件管理的角色。

而 Windows 的 API 有數萬個。Wine 從 1993 年一路做到今天，還是沒有做完。更頭痛的是，程式常常依賴文件沒寫的行為、特定版本的怪癖，甚至是 Windows 自己的 bug（說是龐大的技術債也不為過），這些 Wine 也得照樣學起來。這大概是世界上最需要耐心的工作之一。

遊戲還有另一種語言：圖形 API
#

好，視窗開出來了。但視窗裡是黑的。

遊戲引擎透過 圖形 API 跟 GPU 溝通：上傳模型與材質、設定渲染狀態、要求畫出一批三角形。Windows 遊戲大多說 Direct3D（DirectX 裡負責 3D 繪圖的部分），而 Linux 的 3D 圖形堆疊通常提供的是 OpenGL 和 Vulkan。

所以除了系統 API，圖形 API 也得找人翻譯：遊戲用 Direct3D 說話，相容層要把它翻成 OpenGL 或 Vulkan 聽得懂的指令。

WineD3D：先接到 OpenGL
#

Wine 很早就有自己的翻譯員 WineD3D，用 OpenGL 實作 Direct3D。很多老遊戲就是靠它第一次在 Linux 上跑起來，而且它到今天都還在：Proton 的設定 PROTON_USE_WINED3D=1 可以切回這條路，適用 Direct3D 9 到 11。

問題是兩套 API 的思路差很多。Direct3D 10、11 之後的資源管理、狀態物件與多執行緒方式，在 OpenGL 裡找不到直接對應的東西，WineD3D 只能自己想辦法湊；shader 也得先轉成 GLSL 文字，再讓驅動從頭編譯一次。當遊戲依賴的功能難以有效對應時，就可能掉幀或畫面出錯；結果仍取決於遊戲、驅動與 WineD3D 版本，不能只靠遊戲新舊判斷。

Vulkan：讓工作安排更明確
#

轉機出現在 Vulkan。Khronos 在 2015 年公開 Vulkan，並在 2016 年 2 月 16 日發布 Vulkan 1.0。和 OpenGL 相比，Vulkan 把很多原本由驅動在背後偷偷處理的事，交還給應用程式自己決定：記憶體怎麼配置、命令何時送出、資源之間怎麼同步。

這對相容層來說是天大的好消息。以前 Direct3D 11 驅動在幕後做的那些安排，現在相容層可以在 Vulkan 上親手做，而且照著 Direct3D 的規則做，不必再跟 OpenGL 的假設拔河。當然，Vulkan 本身還是不懂 Direct3D，翻譯員依然少不了，只是手上的工具好用多了。

Shader：繪圖呼叫之外，還有 GPU 程式
#

就算把 Direct3D 呼叫都翻成 Vulkan，也只解決了一半。繪圖呼叫告訴 GPU 要畫什麼；shader 告訴 GPU 每個頂點、每個像素要怎麼算。

舉個例子，遊戲要畫一面被火把照亮的牆。模型和材質只是資料，而「這個頂點要移到螢幕上哪裡」「這個像素在火光下該是什麼顏色」，則是一段跑在 GPU 上的小程式，也就是 shader（著色器）。一款遊戲裡可能有上千個 shader；使用 Direct3D 的遊戲，也通常會附帶 Direct3D 工具鏈產生的編譯結果。

從 HLSL 到遊戲裡的位元碼
#

以較新的可程式化 shader 路徑為例，Windows 遊戲的 shader 通常用 HLSL 撰寫，在開發者的電腦上用 fxc 或 dxc 編譯。隨遊戲發行的，是編譯後的位元碼：舊工具鏈產生 DXBC，Direct3D 12 的新工具鏈產生 DXIL。換句話說，玩家通常拿到的是位元碼，不能假設 HLSL 原始碼也隨遊戲提供。

這就是相容層和遊戲移植最大的不同。開發者移植遊戲時，可以選用支援目標平台的工具重新編譯 HLSL，必要時調整程式；Proton 面對的卻是一款已經發行、可能好幾年沒更新的遊戲。對只提供預編譯 shader 的遊戲，就必須從它附帶的位元碼下手。有點像只拿到一本印好的書，卻要把它翻成另一種語言，作者的手稿早就找不到了。

（嚴格說，DXBC 也是一種容器格式的名稱，DXIL 就裝在這種容器裡，見 LLVM 的說明。所以「D3D12 = DXIL」並不精確，有些 D3D12 遊戲還在用 DXBC。）

Vulkan 為什麼需要 SPIR-V？
#

在本文的通用轉譯路徑中，Vulkan 接收的是 SPIR-V，不能直接把 DXBC 或 GLSL 原始碼交給它。這是 Khronos 定義的一種 shader 中間表示，比原始碼低階，但還沒綁定特定 GPU。驅動拿到 SPIR-V 後，再編譯成自家顯卡的機器碼。

因此相容層的工作就是圖中那一步藍色箭頭：DXBC／DXIL → SPIR-V。兩邊都是結構化的位元碼，比起轉成 GLSL 文字再讓驅動重新解析，可以避免產生與重新解析 GLSL 原始碼的那一層工作。不過型別、資源綁定方式和一些邊角行為仍有差異，不是查字典逐字替換那麼簡單。

shader 與繪圖管線的編譯，是「shader 卡頓」的一個重要來源：如果編譯工作直到遊戲需要畫面時才完成，那一幀就可能晚到。快取與預先編譯能減少這類停頓，但不保證消除所有卡頓。Steam 的著色器預存快取會利用收集到的 shader 與管線資料，減少執行時才遇到的編譯工作；Fossilize 會記錄及重播 Vulkan 物件，讓驅動有機會提前建立本機快取。這不能一概理解成下載一份對所有硬體都能直接使用的 GPU 機器碼。

開源編譯器，與既有遊戲的轉譯
#

說到這裡你可能會問：既然有工具能把 HLSL 編成 SPIR-V，為什麼不用它？確實有。微軟在 2017 年開源了 DirectX Shader Compiler（DXC），它以 LLVM／Clang 為基礎，原本把 HLSL 編譯成 DXIL，後來社群為它加上了 SPIR-V 輸出。對手上有原始碼的開發者，DXC 就是圖中那條虛線捷徑。

但這條 DXC 編譯路徑需要原始碼，而玩家通常沒有。從位元碼出發的那條路，還是得靠 DXVK 與 vkd3d-proton 內建的轉譯器來走。

DXVK 與 vkd3d-proton：把圖形接到 Vulkan
#

目標（Vulkan 與 SPIR-V）都有了，終於輪到真正動手翻譯的兩位主角登場。

DXVK 由 Philip Rebohle 開發，提供 d3d9.dll、d3d10core.dll、d3d11.dll、dxgi.dll 等檔案（2.4 版起也包含 d3d8.dll），在內部用 Vulkan 實作 Direct3D 8 到 11，還自帶把 DXBC（以及 D3D9 時代的 shader 位元碼）轉成 SPIR-V 的編譯器。不過在 Proton 裡，D3D8 一般預設仍交給 Wine 自己的實作；可以用 PROTON_DXVK_D3D8=1 啟用 DXVK，實際選擇也受版本與相容性設定影響。vkd3d-proton 則從 Wine 的 vkd3d 分支出來，專門處理 Direct3D 12，DXBC 與 DXIL 都能轉成 SPIR-V。

最妙的是，遊戲完全不知道自己被掉包了。它照常載入 d3d11.dll、呼叫 D3D11CreateDevice，拿到的物件也乖乖遵守 Direct3D 11 的規則，只是背後的每一個呼叫，其實都在安排 Vulkan 工作。這跟 Wine 替換 kernel32.dll 是同一招，只是用在圖形這一層。想知道兩個專案目前支援到哪裡，可以看 DXVK 與 vkd3d-proton 的說明。

當然，圖形元件只管畫面。檔案、視窗、輸入、執行緒，仍然是 Wine 的工作；遊戲執行時，兩邊的呼叫會不斷交錯。

Proton：把許多專案變成一次 Play
#

Wine 與後來的圖形相容專案，讓許多 Windows 遊戲有機會在 Linux 上執行。在 Proton 出現以前，使用 Wine 與當時可用的圖形元件，通常代表一場小型冒險：自己裝 Wine、建立 prefix、下載對的 DXVK 版本放進去、上論壇翻找某款遊戲需要的神秘環境變數，然後 Wine 一更新，可能又得從頭來過。

Proton 把這整場冒險收進 Steam 的一個按鈕。 Valve 在 2018 年 8 月 21 日公布新版 Steam Play，讓 Windows 遊戲直接透過 Proton 在 Linux 上執行。公告裡也提到，Valve 已經請來 DXVK 的開發者投入開源圖形工作。

Proton 本身是 Wine 的一個分支，再加上 DXVK、vkd3d-proton 與多媒體元件，每個版本一起打包、一起測試。Steam 會替每款遊戲建立獨立的 prefix，減少 A 遊戲的設定影響 B 遊戲的機會。較新的 Proton 版本還會在 Steam Linux Runtime 容器中執行，讓不同發行版使用較一致的使用者空間函式庫，出問題時比較容易重現；GPU 驅動、核心等仍與主機環境有關。Steam Runtime 文件說明了這套執行環境。

這份成果並非 Valve 一家完成。Wine 社群累積了三十年的實作；CodeWeavers 由 Valve 出資，與 Valve 共同開發 Proton；DXVK、vkd3d-proton 與 Mesa 驅動的開發者則守住圖形這一端。

Steam Deck 把這條路放進掌機
#

2022 年 2 月上市的 Steam Deck，跑的是 Linux。它的 SteamOS 3 以 Arch Linux 為基礎；更早的 SteamOS 1、2 則以 Debian 為基礎。完整配置可以看 Steam Deck 技術規格。

Steam Deck 把 Proton 帶進面向一般玩家的掌機，玩家每天使用它，卻不一定需要知道它的名字。很多人買了 Deck、玩了好幾個月，可能都沒意識到自己正在用 Linux。Valve 也為此推出「Deck 驗證」標示，一款款測試遊戲在 Deck 上的表現，讓相容性問題變成開發者看得見、也願意修的項目。可以到 ProtonDB 確認想玩的遊戲是否支援 Proton 在 Linux 上面遊玩，有大量的玩家回報遊玩的狀況。

當然，Proton 不是 Deck 專屬，任何 Linux 桌面上的 Steam 都能用。Deck 厲害的地方在於硬體、驅動、系統與 Proton 可以一起調校，測試目標也比一般桌面 PC 集中；LCD 與 OLED 等機型仍有硬體差異。

從 Wine 到 Steam Deck：發展如何交會
#

回頭看，這其實是三條線的故事：Wine 解決 Windows 環境，圖形專案處理繪圖與 shader，Valve 把元件、驅動和遊戲體驗整合起來。它們起點不同，卻在同一個地方會合。

為什麼還是有遊戲不能玩？
#

講了這麼多，你大概也猜到了：相容層要重現的，是遊戲實際依賴的所有行為，而不只是圖形。常見的卡關點有這幾種：

  • 反作弊：Easy Anti-Cheat 與 BattlEye 從 2021 年起支援 Proton，但每款遊戲的開發者得自己打開這個開關。至於依賴 Windows 核心驅動的反作弊（在核心層掃描記憶體），需要把驅動載入 Windows 核心，而 Wine 底下並沒有 Windows 核心可以載入，目前不受 Proton 支援。Valve 的 Proton 開發者文件列出了這些注意事項。
  • 啟動器與影片：遊戲自帶的登入器、DRM，或用了冷門編解碼器的過場動畫，都可能讓遊戲在主畫面之前就倒下。
  • GPU 與驅動：DXVK 與 vkd3d-proton 需要特定的 Vulkan 功能；比較舊的顯示卡或驅動少了這些功能，Direct3D 12 遊戲尤其容易出事。
  • 更新與回歸：遊戲、啟動器、驅動或 Proton 任何一方改版，都可能讓昨天還好好的組合今天突然壞掉。

效能也只能逐款看。轉譯會多花一點 CPU 時間，shader 與管線編譯可能帶來卡頓；但在部分硬體與測試中，透過 Proton 執行的遊戲甚至比 Windows 還快。「多了一層」不等於「固定慢幾成」。

下次按下 Play
#

最後，回到最開始的那一下。以本文的 Direct3D 11 遊戲為例，Steam 選好 Proton 版本、準備好 prefix，啟動 game.exe。CPU 直接執行遊戲的指令；遊戲呼叫的 kernel32.dll 是 Wine 寫的；d3d11.dll 其實是 DXVK，把繪圖命令翻成 Vulkan、把 shader 翻成 SPIR-V；Vulkan 驅動再把它們編譯好，送進 GPU。順利時，幾秒後你就看到標題畫面亮起；這些相容元件也會在後續遊戲過程中持續工作。

一款沒有 Linux 版本的遊戲，就這樣留在你的遊戲庫裡，不必因為你換了作業系統而被放棄。

下次在 Linux 上按下 Play 時，不妨想一下這個按鈕背後的東西：從 1993 年開始、一個 API 一個 API 補起來的 Wine；讓翻譯員有趁手工具的 Vulkan；一款款遊戲追著修的 DXVK 與 vkd3d-proton；還有把這一切拼成一個按鈕的 Valve。

如果你喜歡這篇文章，強烈推薦去看 Redknot-乔红 的影片 SteamDeck 搭载 Linux，凭什么可以玩 Win 游戏？。我是看了這支影片，才想把 Proton 背後的技術整理成文字。文中的技術細節與時間點，則依各段連結的專案文件和原始公告核對；圖都是概念示意，省略了部分元件與呼叫。
