我把 Claude 用在哪些地方
#

我主要用兩種：Claude（網頁／App）處理日常的各種提問，Claude Code（終端機）處理研究工作，以及其他在電腦上能做的事。不過這些經驗不限於 Claude，現在各家公司的 AI agent 大多都能完成這些任務。

到目前為止，我試過的場景大致可以分為這幾類：

  • 想 idea：發散題目、列可能的方向。
  • 研究：閱讀、整理既有的專案與文獻，從已有的文件、scripts 接下去工作。
  • 投影片與文件：把 Claude 連上 Google Drive，直接修改 Google Docs、Slides。
  • Linux 相關：安裝套件、調整設定、筆電效能優化、修 bug。我覺得 Linux 特別適合這類 AI agent：只要是 Terminal 做得到的事，Claude 大多都能替你完成。
  • 個人網站：就是你正在看的這個網站。
  • 優化自己的工作流程：例如讓 Claude 回頭讀自己的 session 紀錄，找出可以改進的習慣。

這些場景成功的程度差很多。回頭看，決定好不好用的主要是兩件事：結果能不能被驗證，以及需要多少人的判斷。

先理解 Claude Code 的工作環境
#

開始談方法前，有幾個概念先建立起來，後面的技巧都是從這裡推出來的。

一個資料夾就是一個工作空間
#

Claude Code 在哪個資料夾啟動，就以那個資料夾為專案。它讀得到裡面的檔案、會在那裡找 CLAUDE.md 等說明檔。所以「一個專案一個資料夾」本身就是一種管理方式。預設上它不太會主動跑出這個工作空間；如果需要更嚴格的隔離，像 Codex 就有比較嚴格的 sandbox 可以使用。

Harness 決定了它能做什麼
#

同一個模型，放在不同的外殼（harness）裡，能力差很多：網頁版 Claude、Claude Code、其他廠商的 coding agent，各自提供的工具、權限、記憶方式都不同，各有優缺點。大部分能力差不多，相較於 Codex，我比較偏好 Claude Code 在執行長任務時的做法。

一個 harness 大致由這幾個部分組成：

  • 模型：負責思考與決定下一步，例如 Opus、Sonnet。
  • System prompt：告訴模型它的角色、工作方式與規則。
  • 工具：讀寫檔案、執行指令、搜尋網路，或透過 MCP 連接 Google Drive 等外部服務。
  • 權限與 sandbox：哪些操作要先問你、哪些範圍可以碰。
  • Context 管理：開始時載入哪些說明檔、對話太長時何時壓縮。
  • 說明檔與記憶：CLAUDE.md、自動記憶等跨 session 保留的資訊。

模型在這個外殼裡反覆「呼叫工具 → 看結果 → 決定下一步」，直到任務完成。所以同一個模型換了 harness，就像同一個人換了一間設備不同的實驗室。

Context 是有限的資源
#

Claude 在一個 session 裡看得到的內容（context）有上限。對話越長：

  • 越貴：每一輪都要重新處理前面所有內容，額度消耗得更快。
  • 越容易忘：接近上限時舊內容會被壓縮成摘要，細節會遺失；前面交代過的規則也可能被忽略。

快取：為什麼命中了，長對話還是貴
#

前面說「每一輪都要重新處理前面所有內容」，但實際上 Claude 有 prompt caching（提示快取）：剛處理過的內容會暫存起來，下一輪如果開頭一樣，就直接從快取讀，便宜很多。幾個相關的概念：

  • 命中（cache hit）：這次送出的內容，開頭跟快取裡的一模一樣，那一段就直接讀快取。比對是從頭逐字比的（prefix match），中間任何一處改了，從那裡之後的內容都要重新處理。
  • 寫入與讀取的價格：寫進快取比一般輸入貴一點（5 分鐘 TTL 是 1.25 倍，1 小時 TTL 是 2 倍），讀取則便宜很多（大多數模型是 0.1 倍，Opus 5.5 是 0.05 倍）（Anthropic 文件）。
  • TTL（Time To Live，存活時間）：快取放多久會過期。預設 5 分鐘，每次命中都會重新計時，所以只要一直在對話，快取就不會過期。離開超過 TTL 再回來，下一輪就得把整段 context 重新寫入，context 越長，這一下越貴。
  • 會讓快取失效的事：compact 之後，前面的對話換成了摘要，開頭變了，下一輪等於重新寫入；中途換模型（例如從 Opus 切到 Sonnet）也用不到原本的快取。

那為什麼不乾脆都設成 1 小時？因為 1 小時 TTL 的寫入是 2 倍價格，5 分鐘只要 1.25 倍。連續工作時 5 分鐘就夠了，多付的寫入費是白花的；1 小時只有在「常常停 5 到 60 分鐘再回來」時才划算。更重要的是，TTL 只決定快取會不會過期，不會降低每一輪重讀的成本。後面成本那一節的例子裡，session 用的就是 1 小時 TTL，命中率也接近 100%，花費還是很高。

重點是：命中只是打折，不是免費。每一輪都要把整個 context 讀一次，所以 30 萬 tokens 的一輪就算全部命中，讀取成本也是 10 萬 tokens 的 3 倍。

每個 session 開始時，Claude 看到了什麼
#

Claude 本身不會記得上一次對話。每次開新的 session，Claude Code 會先把一批內容放進 context，你還沒打字，它就已經「讀過」這些東西了。依照官方文件，大致包含：

內容存放位置何時載入
System prompt、工具說明、環境資訊由 harness 提供開始時
Skill 描述、MCP 工具名稱安裝的 skill 與 MCP開始時只載入簡短描述，用到時才讀完整內容
全域說明~/.claude/CLAUDE.md開始時，所有專案共用
專案說明專案的 CLAUDE.md 或 .claude/CLAUDE.md（含上層資料夾的）開始時
子資料夾說明子資料夾裡的 CLAUDE.md讀寫該資料夾的檔案時
自動記憶~/.claude/projects/<專案>/memory/MEMORY.md開始時，只讀前 200 行或 25KB

這裡有三種「記憶」，差別在範圍與誰來寫：

  • 全域說明：你自己寫，適用所有專案，例如「回答用繁體中文」、「commit 前先跑測試」。
  • 專案說明：你自己寫（或請 Claude 寫），只適用這個專案。放在資料夾裡，可以跟著 git 同步到其他機器、分享給合作者。
  • 自動記憶：Claude 在工作中自己記下的東西，例如你的偏好、踩過的坑。官方文件明確說它只存在本機（machine-local），不會跨機器同步。

還有一個重點：對話被壓縮之後，專案根目錄的 CLAUDE.md、自動記憶與 system prompt 會被重新載入。換句話說，寫進說明檔的規則撐得過壓縮，只在對話裡交代的不一定。想確認目前 context 被什麼佔用，可以在 Claude Code 裡輸入 /context。

Claude 擅長接手與挑錯，不擅長憑空決定方向
#

擅長的
#

  • 找缺點：像 reviewer 一樣檢查程式、文件、實驗設計，找出漏洞。
  • 具體的指令：描述越詳細，結果越準。
  • 可拆解且可驗證的任務：大任務能拆成小任務，每個小任務都能檢查對錯時，效果最好。
  • 接手已經開始的東西：已經有雛形、有既有檔案時，它很擅長沿著脈絡繼續做；從一張白紙開始反而比較難。

不擅長的
#

  • 決定方向：AI 提的 idea 數量多，但人的 idea 往往更準、更有價值。AI 提出的 idea 往往是已經存在的內容。比較好的分工是人決定方向，AI 負責展開與挑錯。
  • 保證沒有 bug：這是「擅長找缺點」的另一面。每次換一個新的 agent 來檢查，幾乎都能再找出新問題，所以「確定全部正確」需要很多輪迭代，而不是一次到位。

好用的工作方法
#

管理 context
#

  • 一件事一個 session：避免 context 過長帶來的成本與遺忘。換主題就開新的 session。
  • 把重要的東西寫成檔案：CLAUDE.md（專案規則）、PLAN.md（計畫）、EXPERIMENTS.md（實驗紀錄）等。對話會被壓縮、session 會結束，但檔案會留下來，下一個 session 可以從檔案接續。其中 CLAUDE.md 每次開始與壓縮後都會自動載入（見前面的表）；PLAN.md、EXPERIMENTS.md 不會自動載入，可以在 CLAUDE.md 裡寫一句「開始前先讀 PLAN.md」，或用 @PLAN.md 直接引入。

除此之外，像是實驗紀錄可能會越累積越長，最好的做法是把 EXPERIMENTS.md 做摘要，例如 EXPERIMENTS_digest.md，讓模型在新的 session 可以只讀摘要，必要時再做查詢。

以下是我一個攝護腺 CT 分類專案的 CLAUDE.md 節錄（原文為中文，這裡譯成英文；路徑、機器與結果數值都已抽象化）：

# Prostate CT cancer classification (radiomics → DL)

> The radiomics stage is finished and frozen (`SUMMARY.md`, `EXPERIMENTS.md`,
> `outputs/`: **read-only, never overwrite**). Current work is the DL stage.

...

## Data rules
...
- Other files in the parent folder are **not read or referenced**,
  including their conclusions, code and methods.

## Split rules
- `data/split.csv` is the locked train / val / test split. **Never re-split.**
- Model selection and tuning use 5-fold CV inside train only.
- **val only evaluates a configuration already chosen by CV.**
- **test is sealed**: run it once, after the final model is frozen.

...

## Subagent rules
...
- Every subagent prompt carries the full rules: data limits, the locked split,
  test is off-limits, output paths and formats.
- Do not take subagent results on trust: the main agent recomputes key numbers
  before writing them to `EXPERIMENTS.md`.

...

這份檔案的重點不是「怎麼跑」，而是「什麼不能做」：

  • 把評估規則寫死：split 鎖定、只用 CV 選模、val 只評估已選好的設定、test 封存只跑一次。讓它自己跑迴圈時，最容易出問題的就是不知不覺對 val 過度調參，或偷看 test。
  • 限制資訊來源：上一層資料夾有之前的專案，明確寫「不讀、不參考」，避免它直接沿用舊的結論。
  • subagent 也要守規則：每個 subagent 的 prompt 都要帶完整規則；回報的數字由主 agent 重算過才寫進紀錄。
  • 階段完成就凍結：radiomics 做完後設為唯讀，DL 階段另開檔案與資料夾。

搭配的 EXPERIMENTS_DL.md 固定分成四段：目前狀態、進度清單、結果表、逐日紀錄。新的 session 讀前三段就知道進度，細節再往下查：

# DL experiment log

Pass mark: validation AUC > 0.85. Model selection uses train 5-fold CV only;
val only evaluates chosen configurations; test is sealed. Plan: `PLAN_DL.md`.

## Current status (YYYY-MM-DD)
- Best pure DL: <run>, CV <x> / val <y> (95% CI), below the pass mark.
- Bottlenecks: <subgroup A>, <confounder B>.

## Progress
- [x] datalist
- [x] reference architecture, fixed
- [x] <direction 1>, <direction 2>, …
- [ ] final test (once)

## Results table
| run_id | date | input | model | train-CV AUC | val AUC (95% CI) | notes |
|---|---|---|---|---:|---:|---|

## Log
### YYYY-MM-DD Environment and data
- **Incident**: `uv sync` removed packages outside the lock file, including
  the cuDNN library torch needs. Fixed by reinstalling; from now on always
  `uv run --no-sync`.

有些規則是從紀錄裡長出來的。例如某次 uv sync 把 torch 需要的 cuDNN 刪掉了，修好之後，CLAUDE.md 就多了一條「一律 uv run --no-sync」。

管理方向
#

  • Plan mode 與 auto mode：plan mode 先讓 Claude 提出計畫、你確認後才動手；auto mode 則直接執行，由模型分類器代替你逐一核准操作。方向不確定時用 plan mode，任務明確時用 auto mode。差別在於人在哪個時間點介入：plan mode 在動手前，auto mode 在做完後。兩者的效果我認為差不多，依我的使用情境我常常會在過程中有一些想法做補充或是修正（例如上面提到，過程中把某個東西做壞了需要修正），比較接近 auto mode 的使用習慣。

Claude Code 的負責人 Boris Cherny 也說，他和團隊已經好幾個月只用 auto mode，「無法想像回到逐一確認權限的日子」（X 貼文）。他甚至把 auto mode 當成最重要的使用技巧：不用一直停下來等你按確認，才能同時開好幾個 session 平行工作（X 貼文）。依官方說明，auto mode 把核准交給模型分類器，是「人工逐一審核」與「完全不設防」之間的折衷；Boris 自己也提醒它不是絕對安全，用不用取決於你能接受多少風險（Threads）。

  • /advisor：這是 Claude Code 的一個功能，可以讓另一個（通常更強的）模型在關鍵時刻審查目前的做法，像是多一位顧問。除此之外，有的人認為這個可以省下額度（預設使用較弱的模型，例如 Sonnet，將 advisor 設為 Opus）。
  • 人的 idea 優先：先自己想方向，再請 Claude 補充、挑錯，比直接要它出 idea 有效。

擴展能力
#

  • Subagent：把可以平行的工作分給多個子 agent，加速完成；也適合拿來做「獨立的第二意見」。每個 subagent 有自己的 context，做完只把結論交回主 session，所以大量閱讀與搜尋不會塞滿主 session 的 context。我在用多個 agent 發想研究主題裡就是這樣分工：主 session 只負責和我討論與調度，提出想法、質疑想法、查資料各由不同的 agent 負責。

不過 subagent 不是開越多越好。Anthropic 介紹自家多 agent 研究系統時提到，一般 agent 用的 token 約是聊天的 4 倍，多 agent 系統則約 15 倍，所以只有任務價值夠高時才划算。他們也指出，大部分寫程式的任務能真正平行的部分比研究少；需要共用同一份 context、或彼此依賴很多的任務，目前也不適合拆給多個 agent（Anthropic Engineering, 2025）。比較適合交給 subagent 的，是大量閱讀、搜尋，或需要一份獨立意見的工作。

  • Skill / Plugin：把重複的流程包裝起來，下次直接呼叫。例如我把「依照專案結果更新進度報告投影片」做成一個 skill：讀取實驗結果、整理成結果頁與示意圖，寫進 Google Slides 的固定格式。之後只要說「幫我更新這週的投影片」，它就會照同一套流程做，不用每次重新交代格式。目前 Claude 也提供了很多實用的 Plugins / Connectors 可以安裝。兩者的差別大致是：
    • Connector：讓 Claude 連上外部服務、讀寫你的資料。例如 Google Drive／Docs／Slides（直接改文件與投影片）、Gmail、Google Calendar，或 GitHub。
    • Plugin / Skill：把一套做法或工具打包，例如審查目前程式碼改動的 code review、處理 PDF、Word、PowerPoint、Excel 檔案的 skill，或是前端設計指引。
  • 遠端機器：設定好 ssh config 後，可以讓 Claude 到不同的遠端機器上找空閒的運算資源跑實驗。
  • Tmux：讓 Claude 操作 tmux pane，可以管理長時間執行的程式、觀察輸出。在一些需要手動輸入的場合（例如輸入密碼），這個非常實用。

目標明確、可驗證時，讓它自己跑迴圈
#

當專案有明確的目標，而且結果可以驗證，最有效的用法是讓 Claude 自己跑一個迴圈：

這個迴圈在「有清楚目標、可以驗證」的專案上非常好用；細節記錄在上一篇。

還沒解決的問題是預算與停止條件：要給它多少額度？它怎麼知道該停？目前我的做法是把終止條件寫死在 CLAUDE.md，但這需要事先知道目標在哪裡。

預算設定目前我沒有一個完美的解決方案。目前一個比較合適的做法是限定實驗的數量（例如，最多 10 次實驗），但是很大機率會得不到自己要的表現。因此，最好針對自己的任務自行評估。

成本與限制
#

  • 錯誤或是幻覺：現在的模型已經比之前強大不少，但是還是有機率產生幻覺或是提供錯誤的資訊。
  • 安全限制有時太強：有些合理的操作會被安全機制擋下來，需要額外確認或換方式。例如資安方面的問題，有可能會被拒絕回答（即便只在自己的環境做測試），嚴重一點可能會被封號。
  • 輸出不一定好讀：Claude 的寫法常偏「防禦性」，句子保守、限定詞多。寫論文時尤其不理想，需要自己改寫。
  • 會忽略已寫好的規則：即使寫在 CLAUDE.md 裡，它有時還是會忽略。保持說明檔簡短、把最重要的規則放前面，會比較好。
  • 很花錢：要小心管理 5 小時與每週的額度。很明確的任務我會讓 Sonnet 來做，需要判斷或是建議的任務會讓 Opus 來執行。注意不要常常在 context 已經使用不少的情況下對話，可以適時的做 compact 或是開新的 session（原理見前面的快取，實際花費見下面的例子）。換模型也最好在開新 session 時做，中途換會用不到原本的快取。 Context 也不是開越大越好。Claude Code 團隊的 Thariq 提到，在 1M context 的模型上，大約 300–400k tokens 就會開始出現 context rot（模型對前文細節的掌握變差），但門檻依任務而定；他也建議與其等自動壓縮，不如自己帶著提示手動 /compact（X 文章）。所以接近這個範圍時，就是該 compact 或開新 session 的時候。
  • 記憶不跨機器、不跨 App：在不同地方使用 Claude，記憶不會自動同步。如果有一個共用的「第二大腦」讓 Claude 統一管理，應該會很有用。

一個實際的例子：長 context 的花費
#

有一次我發現兩個小時內額度掉得特別快，就請 Claude 回頭分析 session 紀錄。結果幾乎全部來自同一個修改論文的 session：

項目數值
模型呼叫次數308 次（Opus 5.5）
每次呼叫的平均 context約 26.5 萬 tokens（最高約 36.6 萬）
快取讀取8,090 萬 tokens
快取寫入（1 小時 TTL）81 萬 tokens
輸出31 萬 tokens
命中率約 99%

命中率幾乎完美，所以問題不在快取。用 API 價格換算，這兩小時大約 29 美元：重讀 context 佔 56%，寫入快取佔 22%，Claude 真正寫出來的內容只佔 22%。也就是說，光是「每一輪重讀一次」的花費，就是實際產出的 2.6 倍左右，而很多呼叫其實只輸出一行 grep 指令。

為什麼 context 一直這麼大？自動 compact 要等到約 37 萬才觸發，compact 完還剩 11–17 萬，很快又漲回 30 萬以上。兩小時內反覆了三輪，大部分呼叫都落在 20–37 萬之間。膨脹的來源主要是反覆讀取高解析度圖片、每改一處就整份重讀線上文件，以及大量零碎的小指令。

換一種做法：context 到約 15 萬、或一段工作結束時，先把進度寫進筆記，再開一個乾淨的 session，從筆記和需要的文件接著做。我拿同一段工作的每一步重放估算了一下（下圖）：平均 context 從 26.5 萬降到約 8.6 萬，重讀的花費從約 16 美元降到約 5 美元。開新 session 要重新寫入，所以寫入費用略增，但總額仍少了約三分之一。手動 /compact 也有幫助，但這次紀錄裡 compact 完還剩 11–17 萬，起點比乾淨的 session 高很多。重點是提早，而且讓每段工作的起點夠小。

這裡用的是 API 價格。訂閱方案的額度怎麼計算快取，我無法確認是否完全照這個比例，但方向是一樣的：context 越大、呼叫越多，額度就掉得越快。

結語：人負責判斷，AI 負責展開
#

目前為止，大部分的工作還是人機協作，很多地方需要由人來做判斷。如果能把任務拆得更小，並且可以自動化的驗證，那部分就會是 AI 擅長的地方，同時也才能加速自己的工作流程。不過按照目前的發展，或許未來不久的時間，大概也不必弄得這麼麻煩吧！
