這是一份工作流程記錄，不討論任務本身與實驗結果。

任務是一個影像二元分類問題。先後做了兩組實驗：

  • A 組：手工特徵（radiomics）＋表格模型，從 plan mode 開始。
  • B 組：深度學習，沿用 A 組的資料與切分，從 auto mode 開始。

兩組都用同一個迴圈：實驗 → 驗證 → 設計／調整 → 下一組，直到達到明確目標。

目標與規則先寫成檔案
#

開始前先交代三件事，之後都寫進專案的 CLAUDE.md：

  • 明確的終止條件：validation AUC > 0.85。達標後繼續提升，直到連續數輪沒有增益；未達標則持續調整或換方向。
  • 評估規則：切分固定一次並記錄 hash，不再重切。選模與調參只看 training set 內的 5-fold CV；validation set 只用來評估已由 CV 選定的設定；test set 封存，只在使用者決定凍結最終模型後跑一次。
  • 資料限制：只能使用哪些欄位、哪些目錄唯讀、輸出只寫在實驗目錄內。

另外兩份檔案：

  • EXPERIMENTS.md：每輪一列，記錄假設、設定、CV、validation 與結論。
  • 迭代階梯：預先排好的方向清單，由簡單到複雜，每一層確認訊號來源後再往下。

規則寫成檔案的好處是對話被壓縮（context 用完自動摘要）或換 session 時，仍能從檔案接續。A 組與 B 組各經歷過一次壓縮，都沒有影響進度。

一輪迴圈的內容
#

提出假設（下一層特徵／新架構）
  → 背景執行，可續跑、逐筆寫狀態檔
  → 核對：成功筆數、ID 不重複、AUC 可由預測檔重算
  → 只看 CV 決定是否採用
  → CV 選定後評估 validation 一次，記入 EXPERIMENTS.md
  → 消融與錯誤分析，決定下一輪

實際上推動下一輪的通常是以下幾種觀察：

  • 消融找出訊號來源：拿掉哪一組特徵掉最多，就往那個方向補新資訊。
  • 發現 bug：第一輪發現一個欄位過濾條件寫錯，整組特徵幾乎沒有產生，下一輪修正。
  • 模型端飽和：五個模型的預測彼此相關 0.88–0.97，再換模型沒有意義，剩下的槓桿是新資訊，而不是調參。
  • 捷徑檢查：發現有些特徵能區分兩類，但原因是兩類資料的取像方式剛好不同（例如影像涵蓋的範圍長短），而不是目標本身的差異。模型若靠這種線索得分，換一批資料就會失效。因此做了敏感度分析，把這類特徵全部拿掉後重訓，結果幾乎不變，才接受。
  • 無增益就不採用：手工設計的一組額外特徵、分組 late fusion，CV 都沒有提升，記錄後放棄。

A 組的 validation AUC 依輪次為：

輪次主要改變val AUC
1基準特徵0.757
1逐層加入四組區域特徵0.815
2修 bug、新區域、衍生特徵、五模型 ensemble0.841
3第二批分割結構帶來的新特徵0.872（達標）
3敏感度分析：拿掉可疑捷徑特徵0.872

B 組則是另一種結束方式：純深度學習最好到 0.838，未達標。Claude Code 如實回報差距與瓶頸（錯誤集中在哪一類樣本），而不是對 validation 反覆調參湊數字。最後與 A 組凍結的模型做 late fusion 才達標，並標明為混合方法。

「未達標時如實回報，不以對 val 過度調參、動用 test 或規則外的捷徑湊數字」也是寫在 CLAUDE.md 裡的一條規則。

交給 Claude Code 的部分
#

  • 環境（uv）、資料清單、切分、整條 pipeline 的程式。
  • 長時間任務的排程與監看：背景執行，完成時自動通知；訓練時用 Monitor 追蹤每個 epoch 的 log。
  • B 組中自行 ssh 到實驗室其他機器跑實驗，啟動前先看 GPU 是否有人在用。
  • 每輪的消融、錯誤分析與下一步建議。
  • 數字的覆核：寫入紀錄前，由預測檔重算 AUC、核對筆數。

留給自己的部分
#

  • 規則與目標本身。
  • 何時凍結模型、何時跑 test。
  • 根據過去經驗提出方向，例如「預訓練模型應該讓更多比例的權重參與微調」。
  • 設計最後的 ensemble 方式。
  • 研究結束前，要求「把結果沉澱成文件」再 commit，方便下一個 session 接手。

Plan mode 與 auto mode
#

A 組並非全程使用 plan mode：plan mode 只用在開始的規劃，計畫通過後切到 auto mode 執行。B 組則從第一句話就是 auto mode。

A 組：plan mode 開始B 組：auto mode 開始
開頭描述任務與目標，Claude Code 探索目錄後提出計畫一段較長的條件清單
計畫的產生計畫被退回兩次，第三次才通過Claude Code 自己寫 PLAN_DL.md、修改 CLAUDE.md 後直接開始
修正何時發生執行前：退回時補上規則執行中：在對話裡提問與調整
時間約 1.6 天約 1 天

plan mode 的價值在於退回的那兩次。第一份計畫裡，Claude Code 在上層目錄找到過去的實驗結論，並據此規劃方向。這不是我要的：這組實驗應該獨立進行。退回時補上的要求，都在任何程式執行之前進入 CLAUDE.md，之後一天半幾乎不需要介入。

auto mode 少了這道關卡，修正改在執行中發生。好處是可以看到中間結果再提出想法，例如看到預訓練模型只微調部分層後，才建議全層微調；壞處是要更常回來看。

整體感覺兩者差不多。需要注意的是，B 組沿用 A 組已鎖定的切分、分割結果與 CLAUDE.md，起點本來就比較完整。所以這裡的差異主要是「使用者的修正在什麼時候進來」，不能說是模式本身造成結果不同。

觀察
#

  • 明確的數字目標加上固定的評估規則，是讓 Claude Code 能自己跑多輪而不需要每輪確認的前提。
  • 「核對數字」比「跑完了」重要。規則要求結束後核對成功筆數、由預測檔重算 AUC。正式實驗前，Claude Code 也先用打亂的標籤跑一次 pipeline，CV AUC 約 0.46，確認沒有資料洩漏。
  • 捷徑檢查與敏感度分析是 Claude Code 主動做的，結果也如實寫進紀錄。
  • 兩種模式用起來差不多，差別只在修正的時機：plan mode 適合「我已經知道有些事情不想要，但還沒說出口」的情況，auto mode 適合想邊看結果邊調整的情況。Claude Code 的作者 Boris Cherny 也提過他現在用 auto mode 而不是 plan mode，並說團隊幾個月來都只用 auto mode（1、2）。他介紹 auto mode 時舉的例子之一，正是讓模型「反覆迭代直到達到某個效能指標」（3），和這裡的用法相同。
  • 兩組最後都把結果沉澱成文件再 commit，下一個 session（例如準備會議資料）直接從文件開始。

自己跑一次
#

上面的任務與資料不能公開，所以另外做了一個可以自己跑的小範例：claude-loop-demo。

  • 28×28 的乳房超音波小圖，分類良性／惡性，只用 CPU 與 numpy、scikit-learn、matplotlib。
  • 資料夾裡只有資料。規則由你貼一段 prompt 交代，對應上面 B 組的做法：Claude Code 自己寫 CLAUDE.md、實驗紀錄與程式，然後開始跑迴圈。
  • prompt 裡的規則都來自這篇文章：固定切分、val 每輪只評估一次、先用打亂的標籤檢查洩漏、達標前做捷徑檢查、由預測檔重算 AUC。
  • 我跑的那次大約 18 分鐘。
劇透・跑完再看資料做了什麼修改，以及我跑的結果點開

資料改自 BreastMNIST（MedMNIST v2，CC BY 4.0），重新切分，並刻意埋了一個捷徑：部分影像的左上角像素 [1:3, 1:3] 亮度加 70，看起來像機器打上的標記。train 中 76% 的惡性影像有標記，良性只有 4%；val 中惡性 93%、良性 4%。這個標記是人為加的，所以這份資料只適合拿來練習，不能用於研究。

我跑的那次結果如下：

輪設定標記CVval算不算數
R0打亂標籤檢查–0.50–0.54–沒有洩漏
R1原始像素 + 邏輯迴歸沒遮0.8980.953✗ 訊號在左上角標記
R2同 R1遮掉0.7830.741✗ 沒達標
R3HOG + 像素 → PCA → SVM，左右翻轉增強遮掉0.8020.804✓
  • 正式建模前的資料檢查就看到了左上角的亮點，也記錄了「只看這個方塊，val AUC 就有 0.95」，並註明這個數字沒有拿來做任何選擇。
  • 打亂標籤的檢查通過，但它在紀錄裡寫明：這個檢查只抓得到 pipeline 的洩漏，抓不到資料本身的捷徑。這正是這個範例想示範的差別。
  • R1 第一次「達標」後沒有停，捷徑檢查的圖顯示訊號幾乎都在標記上，所以判定不算數。
  • R3 達標後，它另外換了 5 種 CV 切法確認穩定度（平均 0.814），然後就停下，沒有再拿 val 調整。

重點回顧
#

不論是原本的兩組實驗，還是這個 18 分鐘的小範例，能讓 Claude Code 自己跑下去的都是同樣幾個環節：

  • Loop：實驗 → 驗證 → 調整 → 下一輪。 迴圈本身很好建立，難的是何時停。所以終止條件要是明確的數字，再加上輪數上限；沒達標就如實回報差距，而不是無限跑下去。
  • 規則先寫成檔案。 目標、切分、val 的用法寫進 CLAUDE.md，每輪結果寫進 EXPERIMENTS.md。對話會被壓縮、session 會結束，寫進檔案的規則才撐得過去，下一個 session 也能從檔案接手。
  • 驗證機制：「核對數字」比「跑完了」重要。 打亂標籤確認沒有洩漏，由預測檔重算 AUC、核對筆數，val 每輪只看一次。結果能被驗證，才適合放手交給它。
  • 捷徑檢查：達標不等於成功。 打亂標籤只抓得到 pipeline 的洩漏，抓不到資料本身的捷徑。範例裡第一次「達標」靠的是左上角的標記；規則要求先看訊號在哪裡，它才沒有停在這一步。
  • 自我修正迭代。 每一輪的方向來自上一輪的檢查：消融指出訊號在哪、bug 被修掉、捷徑被排除後重跑、沒有增益的方法記錄後放棄。Claude 擅長挑錯，這個迴圈就是讓它一直對自己挑錯。
  • 人負責判斷。 目標與規則、何時凍結、何時跑 test，還是由人決定；Claude 負責在規則內展開與挑錯。
